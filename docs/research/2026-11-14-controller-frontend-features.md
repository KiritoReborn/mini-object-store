# Controller/frontend feature research

Researched 14 November 2026. Documentation and source review only; no runtime or implementation changes. Read `AGENTS.md`, `docs/HANDOFF.md`, `PRODUCT.md`, `docs/DEMO.md`, `DESIGN.md`, `docs/FRONTEND.md`, `docs/LIVE_SYSTEM.md` and the public API contract first. Recommendations below are our assessment, not claims that Artaud implements the reference systems' features.

## Already present: build on these

- [File table](../../frontend/src/components/ObjectTable.tsx): filename-only case-insensitive search, MIME category, name/size/date sorting and ten-row client pagination. [Object listing](../../controller/objects.py) returns every READY object; [database helper](../../controller/database.py) is unpaginated.
- [Upload panel](../../frontend/src/components/UploadPanel.tsx): chooser/drop, serial multi-file queue, actual sending progress, separate controller-confirmation state, per-file cancel/requeue/errors and JSON metadata. A cancelled/interrupted request may already have committed; retry is not idempotent.
- [Inspector](../../frontend/src/components/ObjectInspector.tsx): checksum, metadata, ordered replicas, merge-only JSON metadata edits and explicit single-file deletion. The API has no metadata-key deletion, object rename, folders or upload-resume contract. See [API contract](../../contracts/api-contract.md).
- [System explorer](../../frontend/src/components/SystemExplorer.tsx), [activity timeline](../../frontend/src/components/ActivityTimeline.tsx) and [live contract](../LIVE_SYSTEM.md): selected-file/node filters, quiet summaries, technical events, replay, stale/gap/restart labels and JSON diagnostic/manifest exports. History is bounded to 512 process-local events, not persistent.
- [Demo boundary](../DEMO.md): actual container controls and walkthrough already exist. Workers remain JOINING until B supplies verified recovery admission. More UI cannot make nonempty uploads operational without that dependency.

## Ranked A-only shortlist

Complexity is relative: small = one focused frontend surface; medium = several coordinated frontend/API/test changes. These are sequencing estimates, not calendar promises.

| Priority | Concrete improvement | Complexity | Ownership and acceptance boundary |
| --- | --- | --- | --- |
| 1 | **Find files by useful metadata.** Add clearly named search scopes for name, object ID and custom metadata key/value; optional size/date filters. Start with the existing READY list and export the filtered listing as JSON/CSV with capture time and snapshot status. | Small–medium | A frontend only initially. Match typed JSON consistently; distinguish literal values from substring text. Keep custom metadata out of general diagnostics by default. CSV must quote cells and neutralize spreadsheet formulas. Never download object bodies to search. Inspired by SeaweedFS browsing/properties/export above; metadata-query semantics are our proposal. |
| 2 | **Select several files and act with per-file outcomes.** Visible selection count, explicitly scoped “select this page,” export selected summaries, then confirmed delete of named selected objects. Reuse existing DELETE calls serially; show succeeded, absent, failed and not-attempted rows. Retain failed selection for an intentional retry. | Medium | A frontend using current A API; no new bulk endpoint required. Confirmation states irreversible logical removal and eventual offline cleanup. A lost response is an unknown outcome, not a proven failure or success. Do not silently select hidden/unloaded files. SeaweedFS selection and RustFS tasks supply the pattern. |
| 3 | **Make connection/request failures explainable.** A bounded, in-memory request list: operation, start time, elapsed time, HTTP result or transport failure, and an object ID when known. Offer failure-only filtering and a redacted export alongside existing diagnostics. | Medium | A fetch/upload/download wrappers plus UI; no worker polling or infrastructure. Exclude keys, headers, bodies, custom metadata, raw exception URLs and filenames unless explicitly requested. Label browser end-to-end duration; it includes tunnel/controller/network time and is not storage throughput. Exclude periodic successful polls from the default operation list. Garage's measured durations/errors support this direction. |
| 4 | **Improve queue review.** Aggregate queued byte/file count, stored/failed/cancelled counts, “clear finished,” and explicit “retry selected” after refreshing the object list. Warn when the same browser File is added twice. Keep current serial execution and sending/confirming distinction. | Small | A frontend. No automatic upload retries or overwrite promises; same-name objects can be legitimate, and filename/size is not proof that bytes are identical. RustFS task-panel patterns are relevant; its retry implementation is not a compatible protocol. |
| 5 | **Scale browsing when needed.** Add a separate versioned paginated/search listing route backed by READY-only SQLite queries, stable ordering and bounded page size; preserve the existing list response and helper signature for integrations. | Medium–large | A controller/database/frontend and documented public-contract addition. Avoid speculative indexing or a new service. Implement after measured list sizes justify it; concurrent additions/deletions and cursor semantics need tests. Ceph's [bucket-index design](https://github.com/ceph/ceph/blob/main/doc/dev/radosgw/bucket_index.rst) demonstrates listing from metadata rather than reading object payloads. |

Start with priorities 1–3. They improve the actual demonstration and everyday inspection without new hosting, storage engines or Member B code. Priority 4 is a refinement of shipped behavior, not a new upload subsystem.

## Needs B or a separate contract

- **Integrity-check, scrub, repair/rebalance, rejoin and recovery controls:** B-owned behavior. A may display real results or a proposed API after coordination; it must not promote workers, emulate repair or interpret a successful container Start as verified admission.
- **Physical free space, disk capacity, worker CPU, authoritative worker latency and repair progress:** need measured B-side data and explicit semantics. Recorded replica bytes cannot supply these metrics.
- **Durable operation/audit history:** an A-side SQLite journal is technically possible, but it requires retention, restart/cursor semantics and integration for B-origin operations. Current best-effort post-commit telemetry cannot promise completeness or atomic audit recording. Keep the current bounded observation contract until that work is designed. Ceph's audit facility is precedent for treating this as backend work, not merely a UI label.
- **Resumable/multipart uploads, upload idempotency, folders/rename, versioning, multi-user permissions and S3 compatibility:** separate protocols and data-model work; not required for these improvements or the four-worker assignment demo. Do not add gateways, Prometheus/Grafana services or cloud databases just to imitate reference dashboards.

Verification for any selected implementation should cover real API responses, stale/error states and the affected browser flow; backend behavior should also run through the repository's Linux test suite. Research itself does not prove B's reconciler or an end-to-end recovery demonstration.
